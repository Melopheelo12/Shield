## 1. Durcissement (S0-10) — 15 min

**D'abord, dans le panneau IONOS** (pare-feu du serveur, distinct d'ufw) : ouvrir
**49222 en premier**, puis 22, 80, 21 et 443, en TCP. Garder le 8765. Sans le 49222
ouvert ici, le durcissement coupe l'accès SSH.

Le script est dans le dépôt : on le clone d'abord, dans `/opt/Shield`, le chemin
qu'attend le service de défense active (§ 7).

```bash
git clone https://github.com/Melopheelo12/Shield.git /opt/Shield && cd /opt/Shield
EXTRA_PORTS="8765" ADMIN_USER=antho ADMIN_SSH_PORT=49222 \
ADMIN_PUBKEY="ssh-ed25519 AAAA… antho@portable" \
./scripts/harden_vps.sh
```

## 2. Secrets et `.env` — 10 min

Dans `/opt/Shield`, cloné à l'étape 1 :

```bash
cp .env.example .env && chmod 600 .env
make secrets      # sans make : PYTHONPATH=src python3 -m shield.tools.gen_secrets
```

`make secrets` affiche toutes les lignes ci-dessous avec des valeurs neuves : les recopier
dans `.env` à la place des `change-me…`, et ranger identifiant et mot de passe dans un
gestionnaire de mots de passe.

| Variable | Valeur | Fait |
| --- | --- | --- |
| `SHIELD_ENV` | `prod` : le collecteur **refuse de démarrer** sur un secret `change-me…` ou des identifiants faibles | [ ] |
| `ADMIN_USERNAME` | celui de `make secrets` : `admin`, `root`, `user`… sont refusés | [ ] |
| `ADMIN_PASSWORD` | celui de `make secrets` : 16 caractères au moins, sans le nom d'utilisateur | [ ] |
| `POSTGRES_PASSWORD` **et** `DATABASE_URL` | les deux lignes de `make secrets` (même mot de passe) | [ ] |
| `INGEST_TOKEN`, `BLOCKLIST_TOKEN` | un secret chacun | [ ] |
| `JWT_SECRET` | celui de `make secrets`, 32 caractères au moins | [ ] |
| `ACCESS_TOKEN_TTL_MINUTES` | `240` : la démo ne renvoie pas à l'écran de connexion au bout de 30 min (décision du 26/10) | [ ] |
| `COMPOSE_PROFILES`, `GEOIPUPDATE_ACCOUNT_ID`, `GEOIPUPDATE_LICENSE_KEY` | `geoip` + compte MaxMind | [ ] |
| `ABUSEIPDB_API_KEY` | clé AbuseIPDB | [ ] |
| `DASHBOARD_URL` | `https://localhost:8443` (accès par tunnel) | [ ] |
| `DISCORD_WEBHOOK_URL`, `SMTP_*`, `ALERT_EMAIL_*` | canal de test | [ ] |

Aucun secret ne sort de la machine : rien dans un message, une capture ou une issue.

## 3. Mise en ligne et jalon J4 — 15 min

```bash
docker run --rm -v "$PWD/dashboard:/app" -w /app node:22-alpine sh -c "npm ci && npm run build"
docker compose up -d
docker compose ps        # tout « running » ou « healthy », sauf edge-tls et nginx avant le § 5
docker compose logs collector | tail -30
```

> `edge-tls` (leurre HTTPS) et `nginx` (tableau de bord) lisent tous deux le certificat
> de `/etc/letsencrypt/live/shield/`. Avant le § 5, ils **redémarrent en boucle** : c'est
> attendu, ce n'est pas une panne.

> Un vrai client SSH chiffre la connexion avant d'envoyer un mot de passe, et le leurre
> ne fait pas cette négociation : un événement SSH réel n'a souvent que la bannière du
> client, **sans identifiant ni mot de passe**. C'est attendu. Limite connue : une
> vraie force brute SSH peut être notée comme un balayage (R-005 plutôt que R-007).
> Piste notée au relevé d'Antho du 26/10 (#106), après la pagination du journal.

> ⚠️ La commande de HEBERGEMENT.md § 5 lit `/api/v1/stats/overview` **sans jeton** :
> depuis l'authentification (S3-01), elle répond 401. Lire la base à la place :

```bash
docker compose exec postgres psql -U shield -d shield -c \
  "select count(*) as evenements, count(distinct source_ip) as adresses, max(occurred_at) from event"
```

## 8. Liste blanche de sortie de `core_net` (décision du 22/10) — 30 min

Le traitement sort aujourd'hui librement (#107). Destinations légitimes : DNS,
AbuseIPDB, MaxMind, NVD, CISA KEV, Discord (HTTPS 443) et le SMTP (587).

1. **Repérer par où sort le collecteur.** Il est sur `core_net` **et** sur `web_net`,
   qui n'est pas interne non plus : vérifier lequel porte la route par défaut.
   ```bash
   docker network inspect shield_core_net shield_web_net -f '{{.Name}} {{(index .IPAM.Config 0).Subnet}}'
   docker compose exec collector cat /proc/net/route   # destination 00000000 = route par défaut
   ```
2. **Tester les règles à la main**, sur le ou les sous-réseaux trouvés :
   ```bash
   SUBNET=172.x.0.0/16        # répéter la dernière ligne pour chaque sous-réseau trouvé
   iptables -N SHIELD-EGRESS
   iptables -A SHIELD-EGRESS -m conntrack --ctstate RELATED,ESTABLISHED -j RETURN
   iptables -A SHIELD-EGRESS -d 172.16.0.0/12 -j RETURN    # trafic entre conteneurs
   iptables -A SHIELD-EGRESS -p udp --dport 53 -j RETURN
   iptables -A SHIELD-EGRESS -p tcp -m multiport --dports 53,443,587 -j RETURN
   iptables -A SHIELD-EGRESS -j DROP
   iptables -I DOCKER-USER 1 -s "$SUBNET" -j SHIELD-EGRESS
   ```
   Retour arrière : `iptables -D DOCKER-USER -s "$SUBNET" -j SHIELD-EGRESS`, puis
   `iptables -F SHIELD-EGRESS && iptables -X SHIELD-EGRESS`.
3. **Vérifier**, puis **reporter ces règles dans le bloc `DOCKER-USER` de
   `scripts/harden_vps.sh`**. Ce bloc vide la chaîne (`-F DOCKER-USER`) à chaque
   rechargement d'ufw : des règles ajoutées à la main disparaîtraient. → PR d'Antho.

| | Vérification | Résultat |
| --- | --- | --- |
| [ ] | Le collecteur joint encore AbuseIPDB et CISA KEV ; `geoipupdate` joint MaxMind ; le test Discord passe | |
| [ ] | Depuis le collecteur, `python -c "import socket; socket.create_connection(('1.1.1.1', 80), 5)"` **échoue** | |
| [ ] | Les leurres n'ont toujours **aucune** sortie (`make qa-egress`) | |
| [ ] | Les règles survivent à `ufw reload` (après la PR sur `harden_vps.sh`) | |

> Limite à dire à l'oral : c'est une liste blanche **par port**, pas par domaine. Elle
> empêche un conteneur compromis de scanner ou de joindre un service arbitraire, mais
> pas d'atteindre n'importe quel site en HTTPS. Le filtrage par domaine demanderait un
> proxy sortant : c'est hors périmètre.
